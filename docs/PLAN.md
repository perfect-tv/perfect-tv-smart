# План реализации

Отмечается по мере готовности. Фаза заканчивается сборкой (`npm run build`), тестами (`npm test`) и проверкой в браузере 1920×1080 или в симуляторе.

## Решения (2026-09-26, согласовано с пользователем)

- Минимум — **webOS 3.0** (Chromium 38): сборка в ES5 (esbuild → tsc), полифилы; потоковая загрузка без `fetch`-потоков — куски `Range` или сессия прокси.
- Стек: TypeScript без фреймворков; обычные окна — DOM, гид — Canvas; HLS — hls.js 1.5, запасной — встроенный плеер ТВ; данные — IndexedDB и localStorage; распаковка — fflate.
- Сеть — JS-сервис webOS (Node) как локальный прокси `127.0.0.1:47380`: CORS, заголовки каналов, потоковое чтение на старых ТВ. На ПК тот же прокси — `npm run proxy`.
- Проверка — Chromium 1920×1080 и webOS TV Simulator 6.0 (старее у LG нет); `ares-cli` — в зависимостях проекта.

## Обновление 1.0.7 — SQLite3 и WebSocket (требуется проверка на LG)

При сохранении 1521–4975 каналов на webOS 05.20.15 браузерная IndexedDB
продолжала выдавать `QuotaExceededError` даже после сжатия M3U.
Новая архитектура **не использует IndexedDB или localStorage для записи данных**.

- **`ws://127.0.0.1:47380/db`** — WebSocket (RFC6455) в том же Node-сервисе,
  который уже обслуживает IPTV-прокси; не открывает дополнительный TCP-порт.
- **`/media/internal/perfecttv-data/perfecttv.sqlite3`** — настоящий SQLite3-файл с
  таблицей `kv(s TEXT NOT NULL, k TEXT NOT NULL, v TEXT NOT NULL)`. Весь доступ
  только через `get/put/list/delete/deleteRange/reset/status`, произвольный SQL
  из интерфейса не принимается.
- SQLite формируется и читается ES5 JavaScript-модулем `service/sqlitekv.js`:
  прямой разбор B-дерева SQLite3, UTF-8 и overflow-страниц, атомарная
  перезапись временного файла через `rename`. **Это не нативный модуль sqlite3
  и не полноценный движок SQL**: он реализует только необходимый KV-протокол.
  Причина: старый Node 0.12.2 на телевизоре не поддерживает привычные свежие
  двоичные модули и WASM. Файл проверяется внешним стандартным SQLite3.
- `src/data/socketdb.ts` работает из WebView и EPG Worker. Каналы, плейлисты,
  источники и данные EPG, сопоставления и все настройки/избранное/напоминания
  идут в SQLite по WebSocket. Сжатые записи передаются в base64.
- До создания интерфейса однократно переносятся записи старых IndexedDB,
  файлового хранилища 1.0.6 и localStorage. Старые данные **не удаляются**;
  маркеры миграции предотвращают повторный импорт удалённых значений.
- Если SQLite/WebSocket недоступен, предыдущие данные можно прочитать, но
  новые записи **не делаются в заполненное браузерное хранилище**.
- В «Настройки → Сеть» показан статус `База SQLite3 (WebSocket)`.

**Местные проверки:** 53 теста веб-интерфейса, тесты сервиса/файлового
хранилища, SQLite3 `PRAGMA integrity_check = ok`, взаимодействие по WebSocket,
проверка ES5 синтаксиса, упаковка IPK. На настоящем LG ещё не проверено.
Сервис при каждой записи перестраивает таблицу целиком, поэтому очень
большой XMLTV может работать медленнее обычного нативного SQLite3.

**Проверка:** установить поверх 1.0.6; в журнале должны появиться
`sqlite websocket ready SQLite3`, `SQLite settings ready`,
`sqlite migration ...`; в «Сеть» — `База SQLite3: Подключена`.
Затем обновить M3U, проверить EPG, перезапустить приложение и убедиться, что
плейлист и избранное остались. Не удалять приложение до проверки миграции.

## 1.1.0 — хранилище в файлах сервиса вместо самописного SQLite (2026-10-04)

Версия тестировщика 1.0.9 (правки ChatGPT: QR-ввод, Luna-поток, хранение и разбор программы в сервисе) внесена в репозиторий как есть (ветка `service-files`), поверх неё:

- **`service/filekv.js`** вместо `sqlitekv.js`: тот же протокол (`get/list/put/delete/deleteRange/epgBatch/status/reset`) по WebSocket. Мелкие хранилища — JSON-файл на хранилище в памяти сервиса, запись с задержкой и атомарной заменой; программа — файл на канал и загрузку (`prog/<источник>/<канал>/<загрузка>.ndjson`), пачки только дописываются, старые загрузки удаляются файлами. Самописный SQLite держал всю базу в памяти и на каждую пачку перекодировал и перезаписывал файл целиком — в том же процессе, что проксирует видео.
- **Разбор программы — в дочернем процессе** (`epg-child.js`, `epgrunner.js`): данные пишет родитель; дочерний не запустился — разбор в процессе сервиса. Дочерний процесс завершается вместе с сервисом.
- **Перенос с 1.0.7–1.0.9**: настройки, плейлисты, каналы, сопоставления — из файлов самописного SQLite (основной — если не больше 40 МБ), программа скачивается заново; старые файлы удаляются.

## 1.1.3 — программа в браузере по суткам (2026-10-18)

Браузер держал программу канала целиком (в среднем 650 передач, до 13 тысяч; 70% текста — описания) для 300 последних каналов — на ТВ узким местом становился браузер.

- **Сервис:** в конце загрузки канал собирается в `<загрузка>.epg`: строка `PTV1 <длина>`, оглавление `[[сутки, смещение, длина, передач], …]`, затем по gzip-куску на сутки UTC (по началу передачи). Файлов столько же, сколько каналов.
- **`/prog?s=&x=&a=&b=`** — сутки a…b. Одни сутки из `.epg` — кусок как есть с `Content-Encoding: gzip`; несколько суток, идущая загрузка (`.ndjson`) или прежний `.json.gz` 1.1.1 — сервис собирает и отдаёт обычный JSON.
- **Интерфейс:** `Repo.range(ch, from, to)` вместо `programmes(ch)` — кэш кусков «канал + сутки» (плюс накануне — передача, начавшаяся вчера), недостающие сутки — одним запросом на отрезок, не больше 4 запросов сразу, новые первыми (удержание ↑/↓). Предел — 40 000 передач во всех кусках, выбрасываются давно не нужные. Список программы в гиде перестраивается по `revOf(ch)` с сохранением выбранной передачи.
- **Поиск** — `POST /progsearch` (text/plain, без OPTIONS): сервис перебирает файлы каналов, браузер получает только найденное; новый запрос отменяет прежний. Без сервиса — по каналу из базы.

## 1.1.5 — архив по catchup-days, «Нет программы», программа не теряется при обновлении (2026-10-24)

- Архив в N дней — ровно последние N × 24 ч (`DayWindow.from = сейчас − N × 24 ч`), а не с начала суток: при одном дне в 23:00 расписание начинается с передачи, что шла вчера в 23:00 (22:00–23:30), без архива — с текущей. Передача на границе — со значком архива.
- Даты архива — всегда, даже без программы; там «Нет программы» по 30 минут (или до ближайшей передачи), с архивом.
- Сервис: в конце загрузки (`finalizeSource(s, load, keepFrom)`) прошедшая программа прежней загрузки, которой нет в новой, переносится в новую — что раньше первой передачи новой загрузки и не старше окна архива (`сейчас − (глубина + 1 сутки)`); у канала, пропавшего из XMLTV, — только прошедшее (оно уходит, когда выйдет за окно). Тест — `tools/test-keep.js`.
- Браузер: архив 10 дней при программе с 8.11 — даты с 5.11, 5.11 с 01:24 (граница архива) — «Нет программы» по 30 мин; архив 1 день в 01:24 — список с передачи 00:45–03:35 вчера.

## 1.1.9 — webOS 3: приложение не запускалось (2026-11-01)

- **Вызов своего сервиса запрещён.** Пустые `"requiredPermissions": []` и `"requiredACG": []` в `appinfo.json` на webOS 3 закрывают приложению вызовы по Luna: «Denied method call "ping" for category "/"» (из оболочки `luna-send-pub` тот же метод отвечал). Поля убраны.

- **Папка данных недоступна.** У JS-сервиса webOS 3 нет прав на `/media/internal` (EACCES). `service/datadir.js` выбирает первую доступную на запись: `/media/internal/perfecttv-data` → `/media/developer/perfecttv-data` → `$HOME/perfecttv-data` → папка сервиса → `/tmp`; выбранная — в ответе `ping` (`dataDir`). На эмуляторе webOS 3 — `$HOME` сервиса (его собственная папка), на webOS 4 — по-прежнему `/media/internal/perfecttv-data`.

После исправлений на webOS 3: сервис, плейлист (300 каналов), программа (iptvx), логотипы, HTML-гид — работают (снимок с экрана машины). - Фоновая загрузка программы идёт в `epg-child.js` (отдельный процесс, на эмуляторе ~40% ядра около минуты) — интерфейс не тормозит. ## 1.1.12 — меньше работы браузеру при отрисовке HTML-гида (2026-11-14)

- **Индикатор загрузки программы** проверен по шагам (раз в 3 с: флаг интерфейса и процессор `epg-child.js`): горит, пока процесс работает, гаснет вместе с ним — исправлять нечего.
- **Сборщик мусора** при непрерывной отрисовке гида — 1,4% времени (не 4%, как казалось по короткому профилю). Всё равно убрано лишнее: `measureText` — один объект результата и кэш по шрифтам без склейки ключа, размеры в px сравниваются числом до сборки строки, ячейки строки сетки — из кэша по каналу, окну и номеру изменения программы (`Repo.revOf` учитывает и сброс программы, и загрузку сопоставления). Сборщик — 1,2%.
- **Главное — записи стилей.** Учёт «что уже выставлено» перенесён с полей DOM-узлов в обычные JS-записи (`Rec` в `domctx.ts`), размеры и адрес картинки читаются раз на картинку. Профиль показал, что основное — сами записи стилей: на одну смену канала их было 366, из них ~440 изменённых свойств шрифта, высоты строки и цвета — общий набор текстовых элементов доставался то названию канала, то передаче. Теперь набор текста — свой на каждый шрифт: 144 записи (из них 129 — `z-index`, порядок наложения), шрифт и цвет не переписываются.
- Отрисовка гида (120 кадров со сменой канала, медиана, те же данные): webOS 4 — 1.1.11 4,3–5,1 мс → 1.1.12 3,3–4,2 мс; webOS 3 — 1.1.9 5,9 мс → 1.1.12 3,1–3,7 мс. Вид на webOS 3 и 4 — без изменений (снимки).

## Tizen: заголовки канала через AVPlay (2026-11-18)

Каналы с `#EXTVLCOPT:http-user-agent` / `#EXTHTTP` на Tizen (прокси нет) играют через AVPlay с заголовками: `USER_AGENT` и `COOKIE` (`setStreamingProperty` после `open`, до `prepare`). Раньше UA ставился только в эфире в режиме «авто»: архив, настройка «hls.js» и откат после ошибки шли через hls.js, а он заголовков не ставит. `Referer` и прочие заголовки AVPlay не умеет (в документации Samsung из заголовков запроса только USER_AGENT и COOKIE) — теряются, в журнале предупреждение; запасного пути на Tizen нет (своего прокси нет, `?proxy=` у упакованного приложения не задать).
- Проверено, эмулятор Tizen TV 10 (`ptv-tv10`): сервер на ПК отдаёт плейлист потока только с UA `PTVTEST/1.0` и пишет заголовки; канал с UA, Referer и Cookie, архив в режиме «авто» — `native`, `play ready`, на плейлист и сегменты пришли `User-Agent: PTVTEST/1.0` и `Cookie: sess=abc123`, Referer — пусто, в журнале «native player ignores headers Referer». Юнит-тесты `headersForNative`.
- Не проверено: настоящий ТВ (в т. ч. Tizen 3–6), настройка «hls.js» на эмуляторе.
